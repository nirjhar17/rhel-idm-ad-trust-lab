The Problem: Current Challenges

Identity Management Complexity

  • ❌ Duplicate Accounts: Windows (AD) and Linux (local/LDAP) separate
  • ❌ Password Synchronization: Security vulnerabilities, sync failures
  • ❌ Weak Access Control: Inconsistent policies across platforms
  • ❌ Fragmented Audit: Difficult to trace user actions across systems
  • ❌ Compliance Gaps: Inadequate audit trails and access control

Compliance Reality

₹54.78 crore penalties imposed (353 entities)

Violations: Authentication gaps, access control, audit trail deficiencies

The Solution: Cross-Forest Kerberos Trust

What IdM-AD Trust Provides

  • ✓ Single User Identity: AD as source of truth
  • ✓ Single Sign-On (SSO): One password for Windows & Linux
  • ✓ No Account Duplication: Linux users exist only in AD
  • ✓ No Password Synchronization: Eliminates sync vulnerabilities
  • ✓ Centralized Access Control: HBAC rules from one place
  • ✓ Complete Audit Trails: All actions logged for compliance reporting
Active Directory (Windows) ↓ Kerberos Trust Red Hat IdM (Linux) ↓ SSSD Integration Linux Clients

System Architecture

┌─────────────────────────────────┐ │ Active Directory Domain │ │ ├─ Domain Controllers │ │ ├─ AD Users & Groups │ │ └─ Windows Infrastructure │ └──────────────┬────────────────────┘ │ DNS + Kerberos Trust ┌──────────────┴────────────────────┐ │ Red Hat IdM Domain │ │ ├─ Trust Controllers │ │ ├─ LDAP Directory │ │ ├─ Kerberos KDC │ │ └─ DNS Servers │ └──────────────┬────────────────────┘ │ SSSD Integration ┌──────────────┴────────────────────┐ │ Linux Clients (RHEL) │ │ ├─ SSSD Service │ │ ├─ PAM Integration │ │ └─ Access Control Enforcement │ └──────────────────────────────────┘

Component Responsibilities

  • AD Domain Controllers: Authenticate AD users, maintain directory
  • IdM Trust Controllers: Manage trust, validate credentials, run Samba
  • SSSD (Clients): Mediate authentication, cache identity, enforce access control
  • DNS: Bidirectional name resolution and service discovery

Kerberos Cross-Realm Trust Flow

7-Step Authentication Process

1. AD User Initiates Login (administrator@ad.demo.local) 2. User Authenticates to AD KDC → Receives TGT (Ticket) 3. Client Requests Service Ticket for Linux Resource 4. AD KDC Issues Referral Ticket for IdM Realm 5. Client Contacts IdM KDC with Referral Ticket 6. IdM KDC Validates Trust & Issues Service Ticket 7. Access Granted to Linux Resource ↓ RESULT: Single Sign-On (No 2nd Password!)

Host-Based Access Control (HBAC)

The Challenge

Cannot add AD users directly to HBAC rules (AD users don't exist in IdM LDAP)

The Solution: Three-Tier Group Hierarchy

AD Users (AD Domain) ↓ Add to External Groups (IdM, non-POSIX) Contains AD user references by SID ↓ Add to POSIX Groups (IdM, with GID) Can be used in access control rules ↓ Used in Access Control Policies (HBAC Rules, Sudo Rules, Services)
# Example: Create external group with AD user ipa group-add ad_users_external --external ipa group-add-member ad_users_external \ --external="administrator@ad.demo.local" # Create POSIX group ipa group-add banking_staff ipa group-add-member banking_staff \ --groups=ad_users_external # Create HBAC rule ipa hbacrule-add allow_banking_prod_access ipa hbacrule-add-user allow_banking_prod_access \ --groups=banking_staff

Privileged Access Management (Sudo Rules)

Granting Admin Privileges to AD Users

AD Admin Group ↓ External Group (ad_admins_external) ↓ POSIX Group (admin_group) ↓ Sudo Rule: admin_sudo ├─ Who: admin_group ├─ Where: db-server.idm.demo.local ├─ What: /usr/bin/systemctl, /usr/sbin/reboot └─ Audit: All actions logged!

Configuration Example

ipa sudorule-add db_admin_sudo ipa sudorule-add-user db_admin_sudo --groups=db_admin_group ipa sudorule-add-host db_admin_sudo --hosts=db-server.idm.demo.local ipa sudocmd-add /usr/bin/systemctl ipa sudorule-add-allow-command db_admin_sudo --sudocmds=/usr/bin/systemctl

Audit Result

journalctl -u sudo | grep db_admin@ad.demo.local Jan 19 14:32:01 db-server sudo: db_admin@ad.demo.local : COMMAND=/usr/bin/systemctl restart postgresql

Phase 3: AD Trust Configuration

Configure Trust (20 minutes)

# Install trust packages yum install -y "*ipa-server-trust-ad" # Configure IdM as trust controller ipa-adtrust-install --netbios-name=IDMDOM --unattended # Establish cross-forest trust ipa trust-add --type=ad ad.example.com \ --admin Administrator --password

Verify Trust

# Show trust status ipa trust-show ad.example.com # Test AD user resolution id administrator@ad.example.com # Output: uid=1119000500(administrator@ad.example.com) ✓ # Fetch trusted domains ipa trustdomain-find

Phase 5: Access Control Configuration

Create Access Policies (20 minutes)

# Create external group with AD users ipa group-add ad_admins_external --external ipa group-add-member ad_admins_external \ --external="Administrator@ad.example.com" # Create POSIX group ipa group-add linux_admins ipa group-add-member linux_admins \ --groups=ad_admins_external # Create HBAC rule ipa hbacrule-add allow_admin_access ipa hbacrule-add-user allow_admin_access \ --groups=linux_admins ipa hbacrule-add-host allow_admin_access \ --hosts=idm-client-1.idm.example.com ipa hbacrule-add-service allow_admin_access \ --hbacsvcs=sshd # Create sudo rule ipa sudorule-add admin_sudo ipa sudorule-add-user admin_sudo --groups=linux_admins ipa sudorule-add-host admin_sudo --hosts=idm-client-1 ipa sudorule-add-allow-command admin_sudo --sudocmds=ALL
